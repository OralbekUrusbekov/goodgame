- R-22 — Дочерний документ REST API не содержит спецификации метода для чтения настроек (описано только сохранение, причём через GET-запрос), что делаёт невозможно реализацию чтения настроек мобильным приложением. (Требования к интеграции, строка 52)
- набор — Раздел содержит незаполненные элементы шаблона (указание заполнить позднее); из-за этого спецификация неполна. (Тестирование требований, строка 57)

#### Прочие критические

- R-14 — Правило о максимуме в 1 push за календарный месяц напрямую противоречит пункту Ф-4 (R-16), допускающему повторный push в том же месяце при изменении порога. Сценарий смены порога в текущем месяце блокируется данным ограничением. (Функциональные требования, строка 39)
- R-25 — Критерий приёмки противоречит функциональному требованию Ф-2 («Месяц определяется по дате совершения покупки в Алматы»). Покупка совершена 31 января в 23:58, поэтому относится к январю. При её проведении 1 февраля должен увеличиться январский счётчик, а не февральский. Противоречие блокирует интеграционное тестирование. (Критерии приемки, строка 64)
- R-35 — Формулировка «Проверить сумму и переключатель» не содержит критериев валидации. Кроме того, в спецификации присутствует противоречие: шаг 5 и пример ответа 200 предполагают возврат HTTP 200 с {"result":"ERROR"}, тогда как раздел статусов содержит 400 Bad Request с {"message":"Некорректный запрос"}. Это блокирует реализацию негативных автотестов. (Логика работы метода, строка 119)
