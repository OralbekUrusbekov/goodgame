# Агент проверки требований

Проект проводит статическое ревью документа требований до начала разработки: выделяет атомарные требования, проверяет каждое из них и спецификацию целиком, подтверждает цитаты по исходному тексту и формирует русский отчёт в Markdown и JSON.

## Установка и ключ Gemini

Требуется Python 3.11 или новее.

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
```

Бесплатный ключ Gemini можно получить в [Google AI Studio](https://aistudio.google.com/): войдите в Google-аккаунт, создайте API key и запишите его только в локальный `.env`:

```dotenv
GEMINI_API_KEY=ваш_ключ
```

`.env` исключён из Git. Не добавляйте ключ в исходный код, отчёты или команды. По умолчанию используется `gemini-3-flash-preview`. `LLM_FALLBACK` принимает цепочку `provider:model` через запятую, например `gemini:gemini-2.5-flash,gemini:gemini-2.5-flash-lite`: при исчерпании отдельной квоты агент последовательно переходит к следующей модели, а после исчерпания всей цепочки сообщает список моделей и известное время ожидания. `LLM_CONCURRENCY` задаёт число параллельно проверяемых пакетов (по умолчанию 2); порядок требований в результате остаётся детерминированным.

## Один прогон

```bash
python main.py docs/requirements.md reports/report.md
```

Первый аргумент — входной документ, второй — путь отчёта. Команда создаст:

- `reports/report.md` — отчёт на русском языке;
- `reports/report.json` — структурированный результат того же прогона.

Поддерживаются PDF с текстовым слоем, DOCX, Markdown (`.md`) и обычный текст (`.txt`). Для PDF-сканов без текстового слоя сначала нужен OCR.

## Как проходит проверка

Конвейер выполняет следующие этапы:

1. `loader` читает документ, таблицы, разделы и строки источника.
2. `segmenter` выделяет атомарные требования, присваивает `R-NN` и контролирует покрытие исходного текста.
3. `checker` проверяет каждое требование по свойствам ISO/IEC/IEEE 29148:2018 §5.2.5.
4. `set_checker` проверяет набор по ISO/IEC/IEEE 29148:2018 §5.2.6 и IEEE 830-1998 §4.3: полноту, непротиворечивость, реализуемость, понятность, приоритеты, модифицируемость и трассируемость.
5. `context` при наличии сверяет требования с переданными материалами проекта или read-only GitLab-контекстом.
6. `verifier` проверяет каждую цитату по извлечённому тексту, раскладывает склеенные строки/ячейки на точные фрагменты, определяет раздел/строку и объединяет дубли с общей цитатой и близким смыслом. Неподтверждённые выводы сохраняются для аудита, но не влияют на итог, сводку или список критических дефектов.
7. `reporter` формирует паспорт прогона, нарезку, проверки требований и набора, полную трассировочную матрицу, сводку и итог о готовности к разработке и тестированию. Знаменатель покрытия включает смысловые фрагменты документа и исключает заголовки, пустые шаблоны и процессные метаданные ревью/согласования.

Если любой этап после успешной сегментации завершается ошибкой, `validator.pipeline.run_pipeline` выбрасывает `PartialResultError`. У исключения доступны `stage`, исходная ошибка `cause`, структурированный `payload` той же формы, что обычный результат, и готовый `report_markdown` с явной пометкой частичного отчёта. Это позволяет интерфейсу показать уже выделенные требования и завершённые проверки без ложного итогового вердикта.

Промпты не завязаны на конкретный проверяемый документ. Каталог критериев и их коды находится в `validator/criteria.py`.

## Веб-интерфейс

```bash
python -m web
```

После запуска откройте <http://localhost:8000>. Веб использует тот же конвейер через `validator.contract.run_pipeline`, поддерживает загрузку MD/TXT/PDF/DOCX, прогресс, отмену и скачивание `report.md`.

## Офлайн mock-режим и тесты

Детерминированный провайдер позволяет проверять весь конвейер без ключа, сети и реального LLM:

```bash
LLM_PROVIDER=mock LLM_CACHE=0 python main.py docs/requirements.md reports/mock-report.md
```

Полный набор тестов также принудительно включает mock-режим:

```bash
.venv/bin/python -m pytest -q
```

Тесты покрывают CLI, MD/PDF/DOCX, сегментацию, критерии, проверку и восстановление цитат, веб-контракт, прогресс, отмену, GitLab-контекст, ошибки загрузки и совпадение отчётов CLI и веба. Матрица соответствия хакатонному ТЗ приведена в `docs/COMPLIANCE.md`.
